# Rights Management, License/Expiration Tracking and "Where Used" Tracking for a Cloudflare-based Photo DAM

Research date: 2026-10-16. Prices carry the date on which they were seen, or the source's date. Older sources are flagged inline.

## 1. Standards for rights metadata (IPTC, PLUS, XMP Rights, ODRL/RightsML) and which tools read/write them

### Takeaway
The current IPTC Photo Metadata Standard is **2025.1 (rev 1, 2025-11-26)**. Its rights fields are mostly PLUS-namespace properties in the IPTC Extension schema (`plus:Licensor`, `plus:CopyrightOwner`, `plus:ImageSupplier`, `plus:ModelReleaseStatus/ID`, `plus:PropertyReleaseStatus/ID`, `plus:DataMining`, `plus:OtherConstraints`), plus `dc:rights`, `photoshop:Credit`, `xmpRights:UsageTerms` and `xmpRights:WebStatement`. These are good for embedding a summary of rights in the file. They cannot represent a multi-term license (territory × channel × media × term). That needs a relational license model, with ODRL/RightsML as an optional interchange format. Tool support for the Extension fields is uneven. Photo Mechanic exposes Licensor. Lightroom Classic exposes only some Extension fields, and users report it cannot search or filter on them.

### Cited Findings
**IPTC Photo Metadata Standard: version and changes**
- The current spec is IPTC Photo Metadata Standard 2025.1 rev 1, dated 2025-11-26. It contains IPTC Core 1.5 and IPTC Extension 1.9. The Extension section heading still says 1.8, which is an editorial inconsistency in the document. The URL `iptc.org/std/photometadata/specification/IPTC-PhotoMetadata` redirects to the 2025.1 HTML. — [IPTC Photo Metadata 2025.1](https://www.iptc.org/std/photometadata/specification/IPTC-PhotoMetadata-2025.1.html)
- Change log: **2023.1** added Data Mining (`plus:DataMining`) and Other Constraints (`plus:OtherConstraints`) to IPTC Extension 1.8. **2024.1** approved IPTC Core 1.5, including a change to the Keywords definition. **2025.1** added four AI properties to Extension 1.9: AI Prompt Information, AI Prompt Writer Name, AI System Used and AI System Version Used. — [IPTC Photo Metadata 2025.1](https://www.iptc.org/std/photometadata/specification/IPTC-PhotoMetadata-2025.1.html)

**Rights-related properties and their XMP identifiers (from the 2025.1 spec)**
- Copyright Notice = `dc:rights`. Credit Line = `photoshop:Credit`. Copyright Owner = `plus:CopyrightOwner`. Licensor = `plus:Licensor`. Image Supplier = `plus:ImageSupplier`. Model Release Id = `plus:ModelReleaseID`. Rights Usage Terms = `xmpRights:UsageTerms`. Data Mining = `plus:DataMining`. Image Registry Entry = `Iptc4xmpExt:RegistryId`. Digital Source Type = `Iptc4xmpExt:DigitalSourceType`. — [IPTC Photo Metadata 2025.1](https://www.iptc.org/std/photometadata/specification/IPTC-PhotoMetadata-2025.1.html)
- Model Release Status = `plus:ModelReleaseStatus` (PLUS 1.2, Extension). Property Release Id = `plus:PropertyReleaseID` (Bag of Text). Property Release Status = `plus:PropertyReleaseStatus`. Web Statement of Rights = `xmpRights:WebStatement`, a URL to a page stating copyright and usage rights, added in Core 1.4 / 2017.1 and kept in the XMP Rights namespace. Other Constraints = `plus:OtherConstraints` (Lang Alt, PLUS 1.3, added 2023.1). — [IPTC Photo Metadata 2025.1](https://www.iptc.org/std/photometadata/specification/IPTC-PhotoMetadata-2025.1.html)
- Data Mining values must come from the PLUS controlled vocabulary. The spec describes a value that allows only public search engines to index the asset and its metadata, and prohibits other uses such as AI/ML training. — [IPTC Photo Metadata 2025.1](https://www.iptc.org/std/photometadata/specification/IPTC-PhotoMetadata-2025.1.html)
- PLUS 2.0.1 Data Mining vocabulary URIs follow the form `http://ns.useplus.org/ldf/vocab/DMI-…`. Values: `DMI-UNSPECIFIED`, `DMI-ALLOWED`, `DMI-PROHIBITED-AIMLTRAINING`, `DMI-PROHIBITED-GENAIMLTRAINING`, `DMI-PROHIBITED` (general prohibition), plus the "except search engine indexing" variant. ExifTool uses the same codes with shorter labels. This comes from a forum thread that reproduces the spec, not from the primary PLUS page. — [ExifTool forum, PLUS 2.0.1 Data Mining Field](https://exiftool.org/forum/index.php?msg=82088)
- A separate effort, the IETF AI Preferences (aipref) vocabulary draft, defines TDM, AI Training and Generative AI Training categories. I found no source mapping PLUS DMI values to aipref. — [IETF draft-keller-aipref-vocab-01](https://www.ietf.org/archive/id/draft-keller-aipref-vocab-01.html)
- The Content Authenticity Initiative documents IPTC properties for use inside C2PA manifests. For example, it describes Model Release Status as summarising the availability and scope of model releases, mapped to PLUS. This means the same IPTC fields can travel in C2PA assertions. — [CAI IPTC properties](https://opensource.contentauthenticity.org/docs/manifest/iptc-properties)

**PLUS License Data Format (LDF)**
- PLUS describes the LDF as an ordered set of optional fields for embedding and reading image license metadata. It is a metadata schema, not a licensing interface, and each user decides which fields to use. — [PLUS LDF](https://www.useplus.com/useplus/license.asp)
- Organizations that use the LDF to license or manage their own images may do so free of charge without permission. Including a PLUS standard in an application **sold or licensed to third parties** requires advance permission from PLUS, and so does using the PLUS name or logo. — [PLUS LDF Downloads](https://ns.useplus.com/ldf-Downloads)
- The official pages are on useplus.com / ns.useplus.com, while the namespace URIs use `ns.useplus.org`. I found no 2025–2026 status update for the LDF. — [PLUS LDF](https://www.useplus.com/useplus/license.asp)

**ODRL / IPTC RightsML**
- RightsML is IPTC's model for machine-readable rights expressions (permissions, duties, constraints) for media of any type. It builds on W3C ODRL and extends it for the media industry. The current version is **RightsML 2.0**. Its user list moved to groups.io. IPTC presented RightsML at a W3C workshop on the future of ODRL under the heading "Towards ODRL 3.0". — [IPTC RightsML](https://www.iptc.org/standards/rightsml/)

**Enterprise reference model for rights fields (not a DAM, but a clear schema)**
- Veeva Vault rights records include start and expiration dates, rights countries and license channels. An "Expiring Rights Report" flags items that expire within 90 days. — [Veeva Vault help](https://commercial.veevavault.help/en/gr/1117055/)

**Tool support**
- Photo Mechanic has a full "Licensing" section in its IPTC template and info dialogs. It supports **multiple Licensors** per image, with a Licensor URL that can point to a store (variable `{contactweb}`). Camera Bits documents this mainly for Google Images "Licensable" badges. — [Camera Bits: Licensing on Google Images](https://home.camerabits.com/licensing-on-google-images-what-iptc-fields-to-use-in-photo-mechanic/); [Camera Bits field reference](https://docs.camerabits.com/support/solutions/articles/48001174616)
- Lightroom Classic exposes IPTC Extension fields in its metadata panel, but users report that some Extension fields are missing (2023 feature request). Users also report that "All Searchable Metadata" covers only IPTC Core, so Model/Property Release Status cannot drive filters or smart collections. A January 2025 reply considered that unlikely to change. — [Adobe community: search IPTC Extension fields](https://community.adobe.com/feature-requests-676/p-search-the-iptc-extension-fields-665851); [Adobe community: add newest IPTC Extension fields](https://community.adobe.com/t5/lightroom-classic-ideas/p-add-iptc-extension-fields-from-newest-version-of-iptc-standard/idc-p/13723812)
- The third-party Lightroom plugin "Metadata Panels" adds the newer IPTC Extension fields and a "Releases" tagset. — [Photographer's Toolbox Metadata Panels](https://photographers-toolbox.com/products/mdawson/tpgmetadatapanels/)
- ExifTool can write Model/Property Release Status. — [ExifTool forum](https://exiftool.org/forum/index.php?msg=78618)
- IPTC publishes a vendor-supplied table rating Core and Extension support as many/some/few/no. I could not extract the per-product rows. — [IPTC software support](https://iptc.org/standards/photo-metadata/software-support/)

### Inferences
- Model rights in two layers. (a) An **embedded summary** written into renditions on export or download: `dc:rights`, `photoshop:Credit`, `xmpRights:WebStatement` (a link back to a DAM-hosted license page per asset), `xmpRights:UsageTerms`, `plus:Licensor` (with URL), `plus:ModelReleaseStatus`, `plus:PropertyReleaseStatus`, `plus:DataMining` and `Iptc4xmpExt:DigitalSourceType`. (b) An **authoritative license record** in D1. The embedded fields cannot represent multiple overlapping licenses with territory, channel and term, so they are a snapshot, not the source of truth.
- Lightroom users may not be able to filter on release status. Ingest should read these XMP fields, which may be the first time they become searchable, and normalise the PLUS URIs into enum columns.
- `plus:DataMining` and the IETF aipref vocabulary are both worth exposing as per-asset or per-collection AI-training opt-out settings. Ideally also emit them as HTTP headers or robots signals on public delivery URLs. The header part is my inference; the sources here do not cover it.
- If the open-source DAM bundles the PLUS LDF vocabularies, check the "sold or licensed to third parties" clause with PLUS. Open-source distribution is not clearly covered either way.

### Gaps
- I did not fetch the ODRL 2.2 W3C Recommendation page, so I did not verify its exact date or RightsML's geography/channel/duration vocabulary terms.
- I did not confirm whether `xmpRights:Marked` and `xmpRights:Owner` are referenced in the 2025.1 spec. They are part of Adobe's XMP Rights namespace. I did not verify this with a fetched source.
- I found no source on which IPTC/PLUS rights fields **PhotoShelter** reads, writes or preserves on upload and download. This needs a direct check of PhotoShelter support docs or a test upload.
- I did not find the exact URIs of the Model/Property Release Status vocabulary (PLUS MR-NON, MR-NAP, MR-UMR, MR-LMR etc.) in a fetched primary source.

## 2. How enterprise DAMs model licenses and expiration (Bynder, Aprimo, Orange Logic, Canto, AEM)

### Takeaway
Public vendor documentation is thin. Most native modules offer an asset-level expiration date that triggers a status change, which removes the asset from portals and blocks share and download. Richer multi-dimensional licensing (contracts linked many-to-many to assets, with territory, channel, media and term) is often supplied by add-ons such as FADEL for Aprimo. Webhooks or rules notify downstream systems. Auto-unpublish is known to break live web pages, so vendors pair it with advance warnings.

### Cited Findings
- **Canto:** formerly approved assets with an expiration date automatically get an "expired" status once the date passes. Consumers cannot share or download them, and they are hidden from portals. Canto markets expiration dates as a way to automatically take outdated content out of circulation, alongside approval workflows and DRM. — [Canto Help Center](https://support.canto.com/hc/en-us/articles/23001832933393); [Canto brand solutions](https://canto.com/solutions/brand)
- **Aprimo:** Aprimo's own guidance lists usage terms, expiration dates, geographic restrictions, license details and approval status as rights information to attach to assets. — [Aprimo blog](https://www.aprimo.com/blog/manage-digital-rights-usage-expiration-dam)
- **Aprimo:** for expired content, Aprimo's developer docs recommend **DAM Rules** that make HTTP requests to external systems saying the content no longer has legal rights to be used. In effect these are outbound webhooks. — [Aprimo developer: Expiring Aprimo DAM content](https://developers.aprimo.com/?p=2591)
- **Aprimo:** multi-dimensional rights come from the **FADEL Rights Cloud** connector on Aprimo's marketplace. It links assets to contracts and enforces geography, time period and media-type restrictions, and requires separate FADEL credentials. FADEL Brand Vision adds search by territory, channel and date range. — [Aprimo Marketplace: FADEL Rights Cloud](https://www.aprimo.com/marketplace/fadel-rights-cloud-connector); [FADEL Aprimo connector](https://fadel.com/aprimo-digital-asset-management-connector/)
- **Orange Logic (Cortex):** Orange Logic separates DRM for usage permissions from DRM for content protection (encryption). It advocates automated expiration that holds or restricts an asset without human intervention, plus an audit trail. Its product page offers release and revocation dates and access limits by region, country, state or territory. It lists expiration dates, licence type, terms, duration and renewal as rights metadata. These are vendor marketing pages, and Orange Logic's claimed Forrester Wave ranking is its own characterisation. — [Orange Logic DRM blog](https://www.orangelogic.com/dam-blog/10-top-drm-solutions-and-the-impact-of-digital-rights-management-in-dam-systems); [Orange Logic enterprise DRM](https://www.orangelogic.com/products/enterprise-digital-rights-management); [Orange Logic rights metadata](https://www.orangelogic.com/rights-metadata-in-digital-asset-management)
- **Bynder:** I found no official Bynder docs on rights or expiry behaviour. G2 reviewers rank Bynder strongly on expiration, permissions and access requests, citing collection-level expiration dates. — [G2 discussion](https://www.g2.com/discussions/which-brand-asset-management-platforms-prevent-outdated-materials-with-asset-expiration-and-version-control)
- **Adobe AEM Assets:** AEM ties expiration to licensing, and expired assets are automatically unpublished. Users report that this **breaks asset links on live sites**. Keeping assets published past expiry is not possible out of the box, and the community workaround is a custom scheduler that finds assets nearing expiry. — [AEM DRM docs](https://experienceleague.adobe.com/docs/experience-manager-cloud-service/assets/manage/drm.html?lang=en); [AEM community: unpublishing expired assets](https://experienceleaguecommunities.adobe.com/t5/adobe-experience-manager-assets/what-is-the-best-approach-to-unpublishing-expired-assets-is/m-p/762887); [AEM community: broken links after expiry](https://experienceleaguecommunities.adobe.com/t5/adobe-experience-manager/why-are-asset-links-breaking-on-sites-when-asset-expiration/td-p/726855)
- **MediaValet:** when an expiry date lapses, the asset status changes automatically to Rejected, and it must be manually re-approved before the expiry date can be edited. — [MediaValet support](https://support.mediavalet.com/hc/en-us/articles/7468642240532-How-can-I-clear-the-Expiry-Date-for-an-asset-that-has-Expired)
- **Screendragon:** a Rights tab on each asset holds an Expiration Date after which the asset is "unusable", with an optional auto-archive. — [Screendragon helpdesk](https://helpdesk.screendragon.com/support/solutions/articles/12000106519-managing-asset-rights)

### Inferences
- A suggested D1 model, synthesised from the vendor patterns above:
  - `licenses`: id, licensor/licensee party, contract document key in R2, type (RM/RF/editorial/commercial/exclusive), start, end, renewal terms, notes.
  - `license_constraints`: license_id, dimension (territory | channel | media | industry | print-run | exclusivity), operator, value. These could be ODRL-style constraints.
  - `asset_licenses`: many-to-many, with optional per-asset overrides.
  - `releases` and `release_subjects`: see Q3.
  - A computed `asset_rights_status` derived from all applicable licenses (cleared / restricted / expiring / expired / unknown).
- Effective expiry is the earliest end among the licenses that cover the intended use, not a single field on the asset. The download UI should ask for the intended use (channel and territory) and evaluate it against the constraints.
- Offer a configurable **expiry action** per license or collection: notify only / hide from portals / block downloads / revoke share links / take public delivery URLs offline. Many vendors flag a status rather than hard-unpublish. Hard-unpublishing breaks pages that embed the image, as AEM shows.
- Outbound webhooks on rights-state change, the Aprimo DAM Rules pattern, can run from a Cron Trigger plus Queues.

### Gaps
- I found no first-party documentation for Bynder's rights module or for Orange Logic's expiry configuration and notification settings.
- I found no information on Canto's notification lead times or license entity model.
- Vendor pricing for rights modules was not found.

## 3. Model and property releases: storage, release apps, privacy

### Takeaway
IPTC/PLUS provide status and ID fields only (`plus:ModelReleaseStatus`, `plus:ModelReleaseID`, `plus:PropertyReleaseStatus`, `plus:PropertyReleaseID`). The signed document itself must be stored separately, ideally as a private R2 object linked to people and assets. Release apps such as Easy Release produce a PDF/JPEG plus an ID photo, and I found no evidence they embed IPTC. Releases contain personal data, and linking faces to named people with automated recognition is biometric processing under GDPR.

### Cited Findings
- The IPTC fields are status summaries plus identifiers. Release IDs are a Bag of Text, so several IDs per image are possible. — [IPTC Photo Metadata 2025.1](https://www.iptc.org/std/photometadata/specification/IPTC-PhotoMetadata-2025.1.html)
- Easy Release (ApplicationGap, iOS) collects data and signatures on the device and outputs a PDF and JPEG of the release. It can embed an ID photo of the model in the PDF and auto-save PDFs to Dropbox, Google Drive or OneDrive. I found no evidence that it writes IPTC metadata into its output. — [App Store: Easy Release](https://apps.apple.com/us/app/easy-release-model-releases/id360835268); [PetaPixel (2010, old)](https://petapixel.com/2010/03/11/easy-release-streamlines-model-releases/)
- GDPR Recital 51: a photograph is special-category (biometric) data only when processed through specific technical means, such as facial recognition, that enable unique identification or authentication. — [Presencis: Recital 51](https://presencis.com/regulations/gdpr/recital-51/); [VeraSafe: photographs and special categories](https://verasafe.com/blog/gdpr-and-photographs-understanding-special-categories-of-personal-data/)

### Inferences
- Schema: `people` (name, contact, minor flag plus guardian), `releases` (type model|property, R2 key of the signed PDF, signed date, scope/limitations, expiry if any, source app, release ID) and `release_assets` (many-to-many). On export, the DAM can write `plus:ModelReleaseStatus` and the release IDs into renditions, never the PDF itself.
- Release PDFs and the ID photos inside them are sensitive personal data. Keep them in a separate private R2 prefix or bucket with tighter access control (only rights admins can download) and audit logging. Do not serve them through public delivery URLs.
- Manual tagging of people is ordinary personal data. Automated face clustering that links faces to named people likely requires an Art. 9 condition, such as explicit consent, and probably a DPIA. That is my reading of Recital 51, not a regulator statement. Make face recognition opt-in per tenant, region-aware, and deletable per person (right to erasure must cascade to face embeddings).

### Gaps
- I did not research alternatives to Easy Release (for example Releases by Shuttersnap, Getty/Adobe Stock release apps), whether any have an API or webhook, or whether any write PLUS IDs.
- I found no regulator decision specific to DAM face tagging.
- US state biometric laws (Illinois BIPA, Texas, Washington) were not researched. They are relevant if face recognition is offered to US customers.

## 4. Usage tracking within channels the DAM controls

### Takeaway
"Where used" inside controlled channels comes from two different data sources. (1) **Delivery analytics:** which renditions are fetched, from which referrers, through the DAM's own delivery Worker. Workers Analytics Engine is cheap for this, at 10M data points per month included, then $0.25 per million, with 3-month retention. (2) **Explicit usage records** pushed by CMS integrations, the Bynder "Asset Tracker" pattern with create/list/delete usage API calls. Delivery analytics cannot list every page that uses an asset. Usage records go stale unless integrations delete them.

### Cited Findings
- **Workers Analytics Engine pricing** (seen 2026-10-16). Workers Paid: 10M data points written per month included, then $0.25 per additional million; 1M read queries per month included, then $1.00 per additional million. Workers Free: 100k data points and 10k read queries per day. Cloudflare states it is "not currently billing" for usage and publishes the prices in advance. The price per data point is the same regardless of dimensions or cardinality. — [Analytics Engine pricing](https://developers.cloudflare.com/analytics/analytics-engine/pricing/)
- **Analytics Engine limits:** up to 20 blobs and 20 doubles per data point, one index of at most 96 bytes, at most 16 KB of blobs per data point, and 250 data points per Worker invocation. Retention is **three months**, and longer retention is only by request on Discord. — [Analytics Engine limits](https://developers.cloudflare.com/analytics/analytics-engine/limits/)
- **Bynder Asset Tracker:** shows where an asset is used in integrations, and requires the "View Portal Insights" permission. Custom integrations implement it through asset usage API calls: **create** a usage record when the asset is used externally, **retrieve** usage, and **delete** the record when the asset is removed from the CMS. Bynder SDKs include these calls by default. Integrations include AEM, Bloomreach, Contentful, WordPress, Drupal 8 and Episerver. — [Bynder: How to use the Asset Tracker](https://support.bynder.com/hc/articles/360013933619)
- Bynder's Drupal integration can import assets into the Drupal library or use CDN links, and it sends an asset tracking URL back to Bynder. — [Bynder Drupal datasheet](https://www.bynder.com/m/39a298967e29ca64/original/EN_Datasheet_Drupal-integration_Decision.pdf)
- **Acquia DAM Insights** counts site views, downloads, embed views and share views per asset. Embed links are the way to measure external usage. — [Acquia blog: asset-level analytics](https://www.acquia.com/index%2Ephp/blog/four-questions-to-answer-with-asset-level-analytics.md)
- **AEM Assets Insights** registered usage only when the asset was placed on pages using AEM's embed code, and missed other references. An Adobe Champion notes that web analytics measures what people access, not a full inventory of which assets are used. — [AEM community: asset usage insights](https://experienceleaguecommunities.adobe.com/t5/adobe-experience-manager/aem-dam-asset-usage-analytics-insights-and-reports/m-p/785776/highlight/true)

### Inferences
- **Delivery Worker telemetry:** for each rendition request, write one Analytics Engine data point. Index = asset_id. Blobs = rendition preset, referrer host, referrer path, share-link ID, country, user-agent class. Doubles = bytes, cache status. At 10M points/month included, a mid-size library serving about 300k image views per day stays within the included tier. That is arithmetic, not a vendor quote.
- Retention is 3 months, so roll daily aggregates such as "asset X seen on referrer host Y" into a D1 `asset_usage_observed` table or R2/Iceberg. That keeps a long-lived "first seen / last seen on domain" record. Referrer headers are often stripped (Referrer-Policy, apps, privacy browsers), so treat referrer usage as a lower bound.
- **Usage API:** expose `POST/GET/DELETE /api/assets/:id/usages` (fields: integration, external URL, external ID, placement, created_by, last_verified_at) so that WordPress/Drupal/Contentful/Sanity plugins can report placements. Add a periodic verifier that HEAD-fetches each recorded URL and checks that the asset is still present. This mitigates stale records, the weakness of the Bynder pattern.
- **Download logs with declared use:** record the intended use (channel, territory, campaign) at download time. Validate it against license constraints (Q2), so that "who downloaded what for which use" can be re-checked on expiry and those users notified.
- **Share-link analytics:** give each share link a token. Its views and downloads can go into the same Analytics Engine dataset (blob = link ID). That lets expiring licenses revoke specific links.
- Delivering through DAM-controlled URLs (rather than copies that get downloaded) is what makes both analytics and enforcement possible. An expired asset can be swapped to a placeholder at the edge instead of breaking the page, which avoids the AEM broken-link problem.

### Gaps
- I did not research existing open-source WordPress, Drupal, Contentful or Sanity "DAM usage" plugins beyond Bynder's.
- I did not fetch documentation on the request fields available via Cloudflare Logpush (Referer field etc.) or on its pricing. Logpush is Enterprise-only for HTTP requests, but I did not verify that in this session.

## 5. Usage tracking across the open web: reverse image search APIs, infringement services, perceptual hashing

### Takeaway
As of October 2026 the practical paid APIs for programmatic reverse image search are **Google Cloud Vision Web Detection** ($3.50 per 1,000 after 1,000 free per month; returns `pagesWithMatchingImages`) and the **TinEye API** (prepaid bundles from $0.04 down to $0.01 per search). **Bing Search APIs, presumed to include Visual Search, were retired on 2025-08-11.** Monitoring and enforcement services (Pixsy, Copytrack, ImageRights, Lapixa) operate on contingency fees of roughly 30–50% of recoveries and publish no general public APIs. Self-hosted matching with PDQ or pHash works for comparing known candidates but is not a web-scale discovery engine.

### Cited Findings
**Google Cloud Vision Web Detection**
- Pricing (no effective date on page; seen 2026-10-16): first 1,000 units per month free, **$3.50 per 1,000** units from 1,001 to 5,000,000 per month, and above 5M contact Google. Billing is in 1,000-unit blocks with the last block prorated. — [Cloud Vision pricing](https://cloud.google.com/vision/pricing)
- Returns `webEntities`, `fullMatchingImages`, `partialMatchingImages`, **`pagesWithMatchingImages`** (page URL, pageTitle, matching image URLs on that page), `visuallySimilarImages` and `bestGuessLabels`. `maxResults` defaults to 10. Input can be base64 bytes, a `gs://` URI or a web URL. Google warns that HTTP fetches of remote URLs are not guaranteed and should not be relied on in production. — [Cloud Vision: detecting web entities](https://docs.cloud.google.com/vision/docs/detecting-web)

**TinEye API**
- Prepaid bundles from TinEye's own pricing announcement (post undated): 5,000 searches for $200 ($0.04 each), 10,000 for $300 ($0.03), 50,000 for $1,000 ($0.02) and 1,000,000 for $10,000 ($0.01). These replaced earlier prices of 5,000 for $300 and 30,000 for $1,500. — [TinEye blog: new image search pricing](https://blog.tineye.com/new-image-search-pricing/)
- Purchases are by credit card only. Auto top-up triggers at 75% use. The oldest bundle is consumed first, and searching with no balance returns an error. — [TinEye help: signing up](https://help.tineye.com/article/275-signing-up)
- I could not load TinEye's product page (services.tineye.com/TinEyeAPI returned only a title) to confirm that the bundle prices are still current or to get details on MatchEngine/MulticolorEngine. — [TinEye API page](https://services.tineye.com/TinEyeAPI)

**Bing Visual Search**
- Microsoft retired **Bing Search APIs on August 11, 2025**. Existing instances were decommissioned and new sign-ups stopped. Microsoft points customers to "Grounding with Bing Search" in Azure AI Agents. — [Microsoft Learn: Bing Search API retirement](https://learn.microsoft.com/en-us/lifecycle/announcements/bing-search-api-retirement); [Simon Willison, 2025-05-14](https://simonwillison.net/2025/May/14/bing-search-api-is-being-retired)
- Microsoft's notice covers "Bing Search APIs" as a group. I found no separate notice naming Visual Search, but third-party pages say Visual Search was included and only the bing.com web UI remains.

**Infringement monitoring and recovery services (business models)**
- **Pixsy:** takes a **50% commission** on recoveries, on a no-win-no-fee basis, through partner law firms. — [Inside Imaging, 2019 (old)](https://insideimaging.com.au/2019/pixsy-in-australia/); [Creator Economy Tools profile](https://creatoreconomytools.com/tool/pixsy)
- A user report from several years ago says payouts are split equally net of costs such as court fees. The same report lists paid monitoring tiers at $9.99 and $29.99 per month for 20k and 50k photos, including DMCA takedowns. Sources disagree on the free-tier limit (one says 500 images). — [Croydon Camera Club forum (old)](https://forums.croydoncameraclub.org.uk/viewtopic.php?p=9761)
- **Copytrack** (Germany): monitoring is free for creators, and revenue comes from commission. Reviewers report about 30% in most cases, higher if the case goes to court. Another source says 30–45%, and an industry article says 30–50% depending on complexity and jurisdiction. Copytrack claims to compare more than 240M images per month. Many claims are rejected at screening (wallpaper sites, personal blogs, UGC platforms). — [Light Stalking review](https://www.lightstalking.com/copytrack-review/); [Netcapital profile](https://netcapital.com/companies/copytrack); [SLR Lounge](https://www.slrlounge.com/copyright-infringement-laws-guide-imagerights-copyright-primer-cheat-sheet/)
- **ImageRights:** recovers fees directly or through court with no upfront cost to clients. In 2019 photographer plans cost about $350–$588 per year. In 2010 the recovery split was 35% to ImageRights for paid plans and 50% for the free tier. Both figures are old. Lawyers who defend recipients describe ImageRights demands as "exorbitant", which is not a neutral source. — [Publishers Weekly, 2019](https://www.publishersweekly.com/pw/print/20191118/81754-imagerights-uses-ai-to-fight-copyright-infringement.html); [Photography Blog, 2010](https://www.photographyblog.com/news/imagerights_launches_free_service); [Heitner Legal](https://heitnerlegal.com/2021/11/16/how-to-appropriately-handle-an-imagerights-copyright-infringement-claim-notification/)
- **Lapixa** (Germany): runs automated image search monitoring with enforcement through an international lawyer network (2017). It is positioned as re-licensing rather than warning letters (2016). Commission is not published. — [CEPIC 2017](https://cepic.org/congress/archive/2017/lapixa-sponsor-of-the-cepic-stock-photography-awards); [deutsche-startups.de 2016](https://www.deutsche-startups.de/2016/09/01/lapixa-ein-freundlicher-abmahnservice-fuer-fotografen/?amp=1)
- I found **no public API documentation** for Copytrack, Pixsy, ImageRights or Lapixa in these searches. — [Copytrack search results summary; Light Stalking](https://www.lightstalking.com/copytrack-review/)
- US statutory damages are up to $30,000 per work infringed, or up to $150,000 if willful. Removing an image after notice is not an absolute defense. — [SLR Lounge](https://www.slrlounge.com/copyright-infringement-laws-guide-imagerights-copyright-primer-cheat-sheet/); [Heitner Legal](https://heitnerlegal.com/2021/11/16/how-to-appropriately-handle-an-imagerights-copyright-infringement-claim-notification/)

**Perceptual hashing for self-hosted matching**
- **PDQ** (Meta ThreatExchange) is a DCT-based hash with a quality score. Recommended match threshold: **Hamming distance ≤ 31**. Discard hashes with quality ≤ 49. Reference implementations exist in C++, PHP, Python, Java and **WASM**, with C#/.NET and Rust bindings. PDQ is not exactly rotation-invariant, and hashes vary slightly across languages and image libraries. — [ThreatExchange PDQ](https://github.com/facebook/ThreatExchange/tree/main/pdq)
- PDQ outputs **256 bits** versus 64 bits for classic pHash. It is described as an evolution of DCT pHash, robust to JPEG compression, rescaling and minor edits, and was open-sourced in 2019. — [imghash PDQ docs](https://www.mintlify.com/ajdnik/imghash/algorithms/pdq); [arXiv 1912.07745: PDQ & TMK+PDQF test drive](https://arxiv.org/pdf/1912.07745)
- Third-party ports carry their own licenses: Go port MIT, Rust `pdqhash` Apache-2.0. — [lib.rs pdqhash](https://lib.rs/crates/pdqhash); [pkg.go.dev gopdq](https://pkg.go.dev/github.com/haileyok/gopdq)

### Inferences
- **Recommended open-web pipeline:** on a schedule, send a selected subset of assets (high-value, or "monitor" flagged) to Google Web Detection and/or TinEye. Store `pagesWithMatchingImages` as `asset_web_sightings` (URL, page title, first seen, last seen, match type full/partial). Then classify each sighting against known licensees and authorised domains from the license table and the D1 usage records from Q4. Unknown domains become candidate infringements. Expired-license domains become renewal or takedown candidates.
- **Cost example**, arithmetic from the published prices: monitoring 10,000 assets monthly costs about $31.50 per month on Google (9,000 billable units × $3.50/1k) or $300 on TinEye (10k bundle). Monitoring 100k assets monthly costs about $346.50 on Google or $2,000 on TinEye (two 50k bundles). Google's index is broader but tuned for "web entities". TinEye is better at exact and modified copies. Using both gives better coverage.
- **PDQ in Workers:** a WASM build exists, so hashing at ingest inside a Worker (or a Queue consumer) is plausible. Store the 256-bit hash in D1 and use it for (a) near-duplicate detection in the library and (b) verifying candidate URLs found by Google or TinEye, by fetching the image, hashing it and comparing to the asset. D1 has no native Hamming-distance index, so for large libraries use multi-index hashing (split the 256 bits into 8–16 substrings and do exact-match lookups) or Vectorize with binary vectors. This is my inference, and Vectorize binary support was not verified here.
- **Crawling the open web yourself is not feasible** at a useful scale for a self-hosted DAM. Treat crawling as targeted: re-check known licensee URLs and sighting URLs from the APIs, rather than discovering new ones.
- **Partner with services instead of building enforcement.** Pixsy, Copytrack and others take 30–50% of recoveries. The DAM can offer "export to Pixsy/Copytrack" (CSV or image uploads) rather than an API integration, since no public APIs were found.

- No information was found on **PicDefense**: its model, pricing or API.

## 6. Invisible watermarking and provenance (C2PA, TrustMark, Digimarc, Imatag, Steg.AI, SynthID, Cloudflare)

### Takeaway
C2PA is now at **Content Credentials 2.3 (spec dated 2026-01-05, announced 2026-02-09)**, and a 2.4 soft-binding page is already indexed. Manifests are stripped by most social platforms. C2PA therefore defines **soft bindings**, an invisible watermark or fingerprint that keys a lookup into a manifest repository via a standard Soft Binding API (`/matches/byBinding`, `/matches/byContent`). The registry lists 54 algorithms, including Adobe TrustMark (MIT-licensed, 100-bit payload, open source), Digimarc Validate, Imatag, Steg.AI and Meta PixelSeal/VideoSeal derivatives, but **not SynthID**. Cloudflare Images can preserve and extend C2PA manifests on transforms. c2pa-rs compiles to WASM (`@contentauth/c2pa-wasm`), but running it in Workers is undocumented.

### Cited Findings
**C2PA spec status**
- The Content Credentials 2.3 spec PDF is dated 2026-01-05. C2PA announced it on 2026-02-09. Changes include live video signing (DASH/HLS segments), new formats (plain text, OGG Vorbis, large AVI, EXIF Original Preservation Images), more detailed edit actions (resize, markup, redaction), cloud-referenced trusted information and updated validation and tamper detection. The C2PA Conformance Program launched in late 2025. — [C2PA 2.3 announcement](https://c2pa.org/the-c2pa-launches-content-credentials-2-3-and-celebrates-5-years-of-impact-across-the-digital-ecosystem/); [C2PA 2.3 spec PDF](https://spec.c2pa.org/specifications/specifications/2.3/specs/_attachments/C2PA_Specification.pdf)
- A 2.4 version of the Soft Binding API page is indexed on spec.c2pa.org. Its release date was not verified. — [C2PA Soft Binding API 2.4](https://spec.c2pa.org/specifications/specifications/2.4/softbinding/Decoupled.html)
- One secondary source says v2.2 (May 2025) added cloud-based manifests for formats that cannot embed metadata. — [TrueScreen article](https://truescreen.io/articles/c2pa-standard-history-limitations/)

**Soft binding (watermark/fingerprint → manifest recovery)**
- The Soft Binding API (OpenAPI 3.0.3, API v1.1.0) recovers manifests detached by metadata stripping. Endpoints: `GET /matches/byBinding` (binding value plus algorithm), `POST /matches/byContent` (upload the asset), optional `POST /matches/byReference` (HTTPS URL, with SSRF warnings), `GET /manifests/{manifestId}` and `GET /services/supportedAlgorithms`. Results include a `manifestId`, an optional endpoint and a `similarityScore` from 0 to 100. Auth is OAuth2 client credentials with scope `fetch:manifests`, or unauthenticated. An optional federated lookup uses a distributed-ledger key-value store mapping binding to resolver endpoint. — [C2PA Soft Binding API 2.3](https://spec.c2pa.org/specifications/specifications/2.3/softbinding/Decoupled.html)
- The authoritative **soft-binding algorithm list** (GitHub JSON, 54 entries when fetched 2026-10-16) includes: `com.adobe.trustmark.Q/C/P` (image watermark), `com.adobe.icn.dense` (image fingerprint), `com.digimarc.validate.1`, `com.imatag.lamark.v1`, `ai.steg.api`, `com.microsoft.invismark.1`, `io.iscc.v0` (ISCC, ISO 24138 fingerprint), `com.aiwatermark.pixelseal.1` (Meta FAIR PixelSeal, resolver aiwatermark.com/api/v1), `ai.trufo.pawprint.*`, `castLabs`, `NAGRA`, `MarkAny`, `ContentLens`, `LumaTrace` and others. **No Google SynthID entry.** Entries are added by pull request reviewed by the C2PA Technical Working Group. Being listed is **not** conformance certification, and robustness claims are prose only. — [c2pa-org/softbinding-algorithm-list](https://github.com/c2pa-org/softbinding-algorithm-list); [c2pa-text-binding notes on registration](https://docs.rs/crate/c2pa-text-binding/0.3.0)

**Adobe TrustMark**
- Licensed **MIT**, covering code and model files (models download on first use). **100-bit payload** with configurable BCH error correction: 2 bits reserved, 2 bits select the scheme (BCH_SUPER, BCH_5, BCH_4, BCH_3). Variants Q, P and C appear in the C2PA list. Python (PyTorch) encodes, decodes and removes watermarks. JavaScript (ONNX) is **decode only**. Rust and C++ ONNX runners exist, plus a Raspberry Pi HAILO NPU port. A `/c2pa` example shows how to declare a TrustMark watermark in a C2PA manifest. The README gives no numeric robustness figures. — [adobe/trustmark](https://github.com/adobe/trustmark)

**Commercial watermarks**
- **Digimarc** built C2PA 2.1 manifest recovery on Digimarc Validate, which it calls the first implementation of that standard (October 2024). Subscription tiers exist, but prices are not published. — [BusinessWire, 2024-10-08](https://www.businesswire.com/news/home/20241008536144/en/Digimarc-Brings-Digital-Watermarking-to-the-C2PA-2.1-Standard); [Digimarc blog: C2PA 2.1](https://digimarc.com/blog/c2pa-21-strengthening-content-credentials-digital-watermarks)
- **Imatag:** patented invisible watermark plus monitoring that reports where content appears online and in print. It offers leak identification and an API for DRM/DLP. Customers include newswires and photo agencies. It is enterprise-only with sales-quoted pricing, per an aggregator. — [Capterra: Imatag](https://www.capterra.com.au/software/191439/imatag)
- **Steg.AI** is in the C2PA list (`ai.steg.api`, image/video). I found no pricing. — [c2pa-org/softbinding-algorithm-list](https://github.com/c2pa-org/softbinding-algorithm-list)
- **Google SynthID:** designed to survive lossy JPEG compression, filters and colour changes, but persistence is not guaranteed. It detects only content watermarked at creation by SynthID-enabled generators, so it is relevant to AI-generated images, not to tracking a photographer's own photos. A later report says that in May 2026 OpenAI agreed to apply SynthID to ChatGPT, DALL·E and API images. I found no public third-party detector API. — [TechCabal, 2026-06-25](https://techcabal.com/2026/06/25/what-is-synthid-and-how-does-it-detect-ai-generated-images/); [arXiv 2510.09263 SynthID-Image](https://arxiv.org/html/2510.09263v1)

**Cloudflare**
- **Preserve Content Credentials** in Cloudflare Images (page updated 2026-05-26): when enabled per zone (Images > Transformations), Cloudflare keeps existing C2PA credentials in the source and **adds signed records of the transformation actions**. When disabled, credentials are always removed. Behaviour interacts with the `metadata` parameter, for example `metadata=copyright` keeps the EXIF copyright tag and all Content Credentials. The documentation scopes it to images transformed from **remote sources**. No pricing is mentioned. — [Cloudflare Images: Preserve Content Credentials](https://developers.cloudflare.com/images/transform-images/preserve-content-credentials/)
- A Cloudflare demo signs Workers AI images with Content Credentials using a self-signed demo certificate. Verifiers show "valid signature, untrusted issuer", so production use needs a certificate on a C2PA trust list. — [Cloudflare demo](https://webmcp.demo.chambers.cfdata.org/)

**Open-source C2PA libraries**
- `c2pa-rs` implements C2PA and the CAWG identity assertion: create, sign, parse and embed manifests. `@contentauth/c2pa-wasm` is a wasm-bindgen wrapper around c2pa-rs (Rust ≥ 1.88, wasm32-unknown-unknown) used by `c2pa-web`. — [docs.rs c2pa](https://docs.rs/c2pa/0.75.13/c2pa); [c2pa-wasm docs](https://opensource.contentauthenticity.org/docs/c2pa-js/packages/c2pa-wasm/); [c2pa-wasm README](https://opensource.contentauthenticity.org/docs/c2pa-js/c2pa-wasm-readme)
- A 2024 c2pa-rs change made verify-after-sign conditional on OpenSSL, enabling **signing in non-OpenSSL builds such as WASM**. Older 2022 crate docs said claim generation was unavailable on WASM, which is now outdated. — [c2pa-rs commit mirror](https://archive.git.mtrnord.blog/mtrnords-photography-manager/c2pa-rs/commit/550226f212fe45c4f1029dff497b425469dde512.html); [docs.rs c2pa 0.7.2 (2022, outdated)](https://docs.rs/crate/c2pa/0.7.2)

### Inferences
- **For usage tracking, watermark plus registry beats metadata.** Social platforms strip XMP and C2PA manifests. An invisible watermark carrying a DAM-issued ID (TrustMark's 100 bits fits an asset ID plus rendition or licensee ID) lets the DAM identify a found copy even without metadata. A **per-licensee/per-download watermark**, a forensic watermark, identifies which licensee's copy leaked. This is how Imatag "Leaks" works conceptually.
- **TrustMark is the open-source candidate**, but its encoder is Python/PyTorch (or the C++/Rust ONNX runners) and JS is decode-only. Encoding probably cannot run in a Worker. Run encoding in a container or GPU service (Cloudflare Containers, or AWS Lambda/Batch next to the S3 tier) at rendition time. Decoding through ONNX in a Worker may be possible but is unverified, given Worker memory and CPU limits.
- **The DAM can act as its own C2PA Soft Binding resolver.** Implement `/matches/byBinding` (TrustMark payload → asset/manifest) and `/manifests/{id}` on Workers backed by D1/R2. Third-party C2PA tools could then recover the DAM's manifests. That would be a strong differentiator for an open-source DAM.
- **Cloudflare Preserve Content Credentials** fits if the DAM delivers through Cloudflare Images transformations. Verify that it applies to R2-backed or Workers-binding transformations and not only "remote sources". Sign originals at ingest or export with c2pa-rs (Rust Worker or WASM) using a trust-listed certificate if possible.
- Watermark robustness to aggressive recompression and cropping varies, and the registry's claims are unaudited. Test with a social-media round-trip benchmark before promising survival.

### Gaps
- No vendor pricing was found for Digimarc, Imatag or Steg.AI.
- I found no documentation or reports of c2pa-wasm or c2pa-rs running **inside Cloudflare Workers** (bundle size, memory, signing with keys from Secrets Store). This needs a prototype.
- I did not confirm whether Cloudflare's Preserve Content Credentials applies to images from R2 via the Images binding.
- I did not research Adobe's Content Authenticity app (public beta 2025) and its inspect/registry features.
- No independent robustness benchmark comparing TrustMark, Digimarc and Imatag under Instagram/Facebook/X recompression was found.
- I did not verify the C2PA trust list and certificate costs for production signing.

## 7. Expiration workflows and legal caveats (DMCA, CMI, GDPR)

### Takeaway
Expiration should be a scheduled evaluation over the license table that runs staged notifications (for example 90/30/7 days, the Veeva "90 days" pattern). On expiry it applies a configurable action: flag, hide from portals, block downloads, revoke share links, or swap public delivery to a placeholder. It should also notify integrations by webhook. Legally, stripping rights metadata on delivery can implicate **17 U.S.C. §1202 (CMI)**, so preserve rights fields in renditions. Automated face identification is GDPR special-category processing.

### Cited Findings
- Canto blocks share and download and hides expired assets from portals. MediaValet switches them to Rejected. AEM auto-unpublishes, which breaks web links. Aprimo uses DAM Rules HTTP callouts to tell external systems that rights have lapsed. Veeva runs a report on rights expiring within 90 days. — [Canto](https://support.canto.com/hc/en-us/articles/23001832933393); [MediaValet](https://support.mediavalet.com/hc/en-us/articles/7468642240532-How-can-I-clear-the-Expiry-Date-for-an-asset-that-has-Expired); [AEM community](https://experienceleaguecommunities.adobe.com/t5/adobe-experience-manager/why-are-asset-links-breaking-on-sites-when-asset-expiration/td-p/726855); [Aprimo developer](https://developers.aprimo.com/?p=2591); [Veeva](https://commercial.veevavault.help/en/gr/1117055/)
- **17 U.S.C. §1202:** copyright management information includes the title, author and owner names, copyright notice, **terms and conditions for use**, and identifying numbers or links to such information. It is unlawful to intentionally remove or alter CMI, or distribute works knowing CMI was removed, when the person knows (or, for civil remedies, has reasonable grounds to know) it will induce, enable, facilitate or conceal infringement. — [17 U.S.C. §1202 (Cornell LII)](https://www.law.cornell.edu/uscode/text/17/1202)
- Statutory damages for infringement are up to $30k per work, or up to $150k if willful. Takedown after notice does not cure past infringement. — [SLR Lounge](https://www.slrlounge.com/copyright-infringement-laws-guide-imagerights-copyright-primer-cheat-sheet/); [Heitner Legal](https://heitnerlegal.com/2021/11/16/how-to-appropriately-handle-an-imagerights-copyright-infringement-claim-notification/)
- GDPR: photos become biometric (special-category) data when processed by technical means, such as facial recognition, that enable unique identification. — [Presencis: Recital 51](https://presencis.com/regulations/gdpr/recital-51/)

### Inferences
- **Workflow on Cloudflare:**
  - A daily Cron Trigger queries D1 for licenses whose `end_date` falls inside each notice window. It enqueues notifications to Queues, then Email Sending or webhooks, addressed to the asset owner, the rights admin and every user who downloaded the asset under that license (from the download log in Q4).
  - On the expiry date, the job recomputes `asset_rights_status` and applies the configured action:
    - set the share-link `revoked_at`, which the delivery Worker checks
    - block original and rendition downloads
    - optionally have the delivery Worker return a placeholder or HTTP 451/410 for public URLs, rather than breaking layout
    - post webhooks to CMS integrations so they can swap the image
  - The job also produces an "expiring licenses" report in CSV or an in-app view.
- Because removing CMI can carry liability, rendition pipelines (Cloudflare Images `metadata=` setting, or custom resizing) should **keep copyright and rights fields by default** (`metadata=copyright` at minimum). Do not offer "strip all metadata" for licensed third-party images without a warning. This also argues for C2PA preservation.
- **DMCA takedowns:** the DAM's open-web sightings (Q5) can generate pre-filled §512(c) notice drafts for the user to send. The DAM should not send them automatically, and it should flag that fair use must be considered before sending. If the DAM hosts public galleries, the operator also needs its own DMCA agent and takedown process for user-uploaded content.
- **GDPR** applies to release documents, people records and any face recognition. Use region-pinned storage (R2 jurisdictional buckets, D1 location hints), deletion cascades and opt-in face features. Treat tracking pixels or referrer logging on public delivery as personal data only if IPs are retained, and aggregate them in Analytics Engine without raw IPs.

### Gaps

- I did not research EU equivalents to CMI protection (InfoSoc Directive Art. 7) or the EU DSM Directive Art. 4 TDM opt-out, which is relevant to `plus:DataMining` and should be verified.
- I found no source on HTTP 451 usage conventions for expired-license media, so that is a design suggestion.
- I found no legal sources on liability when a DAM auto-unpublishes images still embedded by licensees, for example contractual sell-off periods. Many RM licenses include grace periods, so the model should support a `sell_off_until` date (inference).
