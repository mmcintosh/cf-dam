# Put a thin agent beside the files

The DAM can do everything this photographer needs. It can reach every mainstream NAS, coexist with Lightroom Classic, NeoFinder and PhotoShelter, and move data off the NAS in ways that can be verified. None of this needs a vendor plugin or a NAS product of its own. It does need the work split along a line the research makes clear. **Every integration with the photographer's existing tools sits on the workstation.** The Lightroom Classic catalog must stay on local disk, its only supported write path is a Lua plug-in running inside LrC, and NeoFinder is a macOS app that can only be automated through AppleScript. **Every safe, verifiable movement of bytes belongs on the NAS.** Over SMB there are no hashes to compare, every cloud upload crosses the LAN twice, and PhotoShelter's one-upload-per-minute API limit turns a delivery into an hours-long job that a sleeping laptop cannot finish. The recommended design is therefore option (b): a small, unprivileged container agent on the photographer's existing NAS, paired with a desktop client. The agent owns the storage ledger: which bytes exist where, under what hash, and when they were last verified. It drives an embedded rclone engine. The desktop client owns the Lightroom and NeoFinder bridges and the editing UI, and it treats XMP in the files as the shared source of truth for metadata. Running that container is no more "building a NAS" than installing Plex or Immich through Synology's Container Manager is. For this first user, the build order is: an LrC-compatible XMP contract plus a read-only catalog import; then verified NAS-to-cloud and NAS-to-drive copies with manifests; then the LrC plug-in; then NeoFinder hooks; and last a PhotoShelter publish target. The DAM should embed rclone, xxHash, a catalog reader and a metadata library, and build only the ledger, the verification policy and the tool bridges.

## Docker, not vendor plugins, is how software reaches a NAS

The first round of research found that the container runtime has become the de facto app platform for NAS boxes. Synology Container Manager, QNAP Container Station, UGREEN UGOS Pro, TrueNAS Community Edition (native Compose since 24.10), Unraid (Docker, with Compose via a community plugin), Asustor, TerraMaster and OMV all run one multi-arch Compose stack. The native package formats (Synology SPK, QNAP QPKG, UGREEN UPK, Unraid CA templates, TrueNAS catalog apps) add signing, review and business-agreement hurdles that a community project cannot easily clear. Synology trusts only Synology-signed packages ([SynoCommunity FAQ](https://github.com/SynoCommunity/spksrc/wiki/Frequently-Asked-Questions)). QNAP's Security Counselor flags unsigned apps ([QNAP FAQ](https://www.qnap.com/en/how-to/faq/con_show.php?cid=2434)). UGREEN's packer accepts a standard Compose file but **rejects `privileged`, `cap_add`, host PID/IPC and `latest` tags** ([UGREEN Docker APP docs](https://developer.ugnas.com/en/doc/backend/quick-start/develop-docker-app.html)). TrueNAS's community catalog excludes apps that "interact with the TrueNAS host management layer or API" ([truenas/apps CONTRIBUTIONS.md](https://raw.githubusercontent.com/truenas/apps/master/CONTRIBUTIONS.md)). **WD My Cloud OS 5 has no supported Docker** and can only be treated as an SMB source ([WD Community](https://community.wd.com/t/docker-support-in-os5/257063)). Immich and Jellyfin reach NAS users through exactly this Compose-first route.

Synology dominates the photographer market. A self-hoster survey of unclear provenance puts **Synology at 62% of pre-built NAS users versus 14.3% for QNAP** ([CommandLinux](https://commandlinux.com/statistics/nas-and-file-server-os-distribution/)), and Fstoppers' 2026 guide names the DS925+ best overall ([Fstoppers](https://fstoppers.com/best-nas-photographers-2026)). Technically minded early adopters lean toward TrueNAS (19.0%) and Unraid (10.1%) ([selfh.st 2025](https://selfh.st/survey/2025-results/)). Vendor APIs are connectors, not foundations. Synology documents a File Station Web API, but its Photos API is undocumented ([File Station API Guide](https://cndl.synology.cn/download/Document/Software/DeveloperGuide/Package/FileStation/All/enu/Synology_File_Station_API_Guide.pdf)). **TrueNAS removes REST in TrueNAS 27 in favour of versioned JSON-RPC over WebSocket** ([TrueNAS deprecations](https://www.truenas.com/docs/scale/26/gettingstarted/deprecations/)). Unraid 7.2 ships a GraphQL API that is mostly status and notifications ([Unraid API docs](https://docs.unraid.net/API/)). No vendor offers a file-change event API.

This round adds the vendors' native backup tools, which the DAM should orchestrate rather than replace. **TrueNAS is the most automatable.** Its Cloud Sync is rclone-based, and the API exposes `cloudsync.sync_onetime` for running a sync without creating a saved task, in versions 24.10 through 26.0 ([TrueNAS API v26.0](https://api.truenas.com/v26.0/api_methods_cloudsync.sync_onetime.html)). Synology Hyper Backup can be started from the DSM Web API, but the only evidence is a community MCP wrapper calling what is presumably `SYNO.Backup.Task`, and **no official documentation was found** ([glama.ai synology-mcp](https://glama.ai/mcp/servers/rafalr100/synology-mcp/tools/run_backup_task)). Hyper Backup also runs one task at a time per client ([Synology KB](https://kb.synology.com/en-my/DSM/help/HyperBackup/data_backup_create?version=6)). QNAP HBS3 supports more than 30 cloud targets, but **no public API was found**. Its QuDedup output is a proprietary `.qdff` format that needs QNAP's extract tool to restore and works only on x86 models ([QNAP HBS3](https://www.qnap.com/solution/hbs3)). Synology is folding C2 Storage into **C2 OneStorage from 22 June 2026**, and legacy plans can be renewed until 22 December 2026 ([NASCompares](https://nascompares.com/2026/05/25/synologys-c2-and-license-changes-explained/)).

Hardware still sets the ceiling on what can run on the NAS. Synology's Ryzen Plus models have **no iGPU**. Its J4125 models top out at 6 GB of RAM. Its j and Value lines are ARM boxes with 1–2 GB. Immich wants at least 6 GB and runs on 4 GB only with ML disabled ([Immich requirements](https://docs.immich.app/install/requirements/)). Synology's Container Manager release notes list some ARMv8 models ([Synology Container Manager release notes](https://www.synology.com/en-uk/releaseNote/ContainerManager)), so a thin agent is plausible even on low-end units. ## Lightroom Classic integrates through XMP, a catalog copy and a Lua plug-in

Lightroom Classic offers four routes for integration, and none of them is complete on its own. The `.lrcat` catalog is an undocumented SQLite database that has to stay on local disk. Its path model is **`AgLibraryRootFolder.absolutePath` + `AgLibraryFolder.pathFromRoot` + `AgLibraryFile.baseName.extension`**, joined through `Adobe_images.rootFile` ([thany gist](https://gist.github.com/thany/1f7a2172129aa4aea258c2971610581a)). These core tables have been stable for more than a decade. The best ready-made reader is **lrcat-extractor**, a Rust library under MPL-2.0. Version 0.7.0 shipped on 12 September 2026 and models root folders, folders, files, images, keywords, keyword trees and collections ([docs.rs](https://docs.rs/lrcat-extractor/latest/lrcat/)). Its README lists catalog versions 2, 4 and 6 only ([GitHub](https://github.com/hfiguiere/lrcat-extractor)), so coverage of LrC 12–15 catalogs needs testing against a real catalog before the project depends on it. Commercial importers set a low bar. Capture One's Lightroom importer brings over collections, ratings, labels and flat keywords, but **drops Smart Collections and every develop adjustment except orientation, crop, white balance, saturation, contrast and exposure** ([Capture One FAQ](https://support.captureone.com/hc/en-us/articles/360003692438-Migrating-from-Lightroom-FAQ)).

Writing to the catalog from outside Lightroom is off the table. LrC creates `.lrcat-wal`, `.lrcat-shm` and `.lrcat.lock` files while it runs. **WAL files left behind after LrC exits mean a crash with unmerged writes** ([Adobe Community](https://community.adobe.com/t5/lightroom-classic-discussions/lrcat-shm-and-lrcat-wal-are-for/td-p/9505585)). LrC 15.5 (August 2026) added an integrity checker for the companion `.lrcat-data` store ([LrC release notes](https://helpx.adobe.com/lightroom-classic/desktop/introduction-to-lightroom-classic/release-notes.html)). The safe protocol is to refuse to read while a lock or WAL file exists, copy the closed catalog to a temp directory, and open the copy read-only. This has to run on the workstation, because that is where the catalog lives.

XMP is the shared contract, but it carries only part of the catalog. With "Automatically write changes into XMP" turned on, LrC writes ratings, keywords (flat and `lr:hierarchicalSubject`), IPTC, `crs:` develop settings and MWG face regions. It writes sidecars for proprietary RAW and embeds XMP in DNG, JPEG, TIFF and PSD ([Lightroom Queen](https://www.lightroomqueen.com/community/threads/when-are-xmp-files-created-for-nef-files.19693/post-133289); [ExifTool Lightroom tags](https://exiftool.org/TagNames/XMP.html#Lightroom)). Several things live only in the catalog ([Adobe Community ideas thread](https://community.adobe.com/t5/lightroom-classic-ideas/p-include-additional-metadata-in-xmp-flags-collections-vc-s-etc/idi-p/12662756)):

| Data | In XMP? | How the DAM gets it |
|---|---|---|
| Rating, keywords, hierarchy, IPTC, develop settings | Yes | Read XMP (sidecar or embedded) |
| Color label | Yes, but as **localized, user-renamable text** in `xmp:Label` | Configurable text-to-enum map ([pixls.us](https://discuss.pixls.us/t/colour-label-in-xmp/8067)) |
| Face regions and names | Yes (`mwg-rs`, center-based coordinates) | Read XMP; convert coordinates ([Adobe Community](https://community.adobe.com/t5/lightroom-classic-discussions/face-image-region-data-written-according-to-xmp-mwg-rs-but-not-read-by-lr/m-p/13771103)) |
| Pick/reject flags, collections, smart collections, stacks, virtual copies, develop history | **No** | Read-only catalog copy, or the LrC plug-in |

Writing back through XMP needs care. LrC does not watch XMP files. A change made by the DAM shows up in LrC as a metadata conflict, and the user's "Read Metadata from Files" overwrites newer catalog values for those fields. The DAM therefore needs a last-writer policy based on `xmp:MetadataDate` and optimistic mtime checks before every sidecar write.

**The Lua SDK is the only supported way to write into the catalog**, and it is capable. `LrCatalog` provides `findPhotoByPath`, `findPhotoByUuid`, `createKeyword`, `createCollection`, `createSmartCollection`, `addPhoto`, `createVirtualCopies` and write-access gates ([LrCatalog reference mirror](https://lrc.mcor.dev/modules/LrCatalog.html)). Publish services track per-photo remote IDs and URLs ([Adobe Community](https://community.adobe.com/t5/lightroom-classic-discussions/metadata-handling-with-several-publish-service-providers/m-p/12498164/highlight/true)). bmachek's lrc-immich-plugin v5 already follows the target pattern of publish, import and two-way catalog sync against a server ([newreleases v5.0.0-pre](https://newreleases.io/project/github/bmachek/lrc-immich-plugin/release/v5.0.0-pre)). There are constraints. A plug-in runs only while LrC is open. Adobe's public SDK download was **"still stuck at v14.3" in November 2025**, so the plug-in should target the 14.x API and feature-detect anything newer ([Adobe Community](https://community.adobe.com/t5/lightroom-classic-discussions/no-lua-sdk-for-lightroom-classic-v15/td-p/15607061)). `LrTasks.execute` subprocesses have had platform-specific bugs on Intel Macs in 13.5 and 14.5 ([Adobe Community bug](https://community.adobe.com/t5/lightroom-classic-bugs/p-plugin-crashes-when-a-plug-in-uses-lrtasks-execute/idi-p/14845263/page/2)), so the plug-in should call an already-running DAM over `LrHttp` rather than spawn helpers. The Lightroom cloud Partner API reaches only cloud catalogs, and only for "entitled partner applications" ([AdobeDocs](https://github.com/AdobeDocs/lightroom-partner-apis)), so it is irrelevant to an LrC user.

Path handling is the trap that matters most for data movement. On Windows, **NAS folders referenced by UNC paths have shown wrong counts or "Invalid Path" errors since LrC 8.4, and a user on 14.3 reported the problem persists**. The community fix is a mapped drive letter plus one "Update Folder Location" on the root folder ([Adobe Community](https://community.adobe.com/bug-reports-674/p-missing-photo-counts-for-folders-with-unc-paths-663523/index2.html)). If the DAM moves files behind LrC's back, they show up as missing. The research did not confirm whether the SDK can relocate a folder. The least damaging move is to relocate whole root folders with their subtrees preserved and then prompt the user to run one Update Folder Location. The DAM should also store LrC's `id_global` UUID and content hashes so it can re-link files without relying on paths.

## NeoFinder is a Mac-only neighbour reachable by XMP and AppleScript

NeoFinder 9.3.1 (29 September 2026) is a perpetually licensed, actively developed macOS cataloger, essentially the work of one developer. Its job is answering "which drive holds that shoot" across NAS shares, external drives, optical media and LTO ([Release notes](https://cdfinder.de/versions.html); [cdfinder.de](https://www.cdfinder.de/)). Its presence tells us something about the first user: **they work on a Mac**. NeoFinder has no Windows version; abeMeda is a separate Windows product that shares its file format ([abeMeda](https://www.abemeda.com/)). That brings in the Mac-specific hazards covered below: NFD filenames, openrsync, and `/Volumes` mount points.

NeoFinder does not parse `.lrcat`. Its manual tells Lightroom users to turn on automatic XMP writing "so that NeoFinder can see and catalog your metadata" ([Catalog Lightroom](https://www.cdfinder.de/guide/3/3.14/catalog_lightroom.html)). **A DAM that writes standard XMP will therefore appear in NeoFinder on its next catalog update without any integration code.** One detail matters. Since version 9.0, NeoFinder **writes XMP directly into ARW, ORF and RW2 raw files instead of sidecars** ([Release notes](https://cdfinder.de/versions.html)), so the DAM must read embedded XMP for those formats or it will miss edits made in NeoFinder. It also has to accept that a third tool may modify raw files in place, which changes their content hashes. The DAM should hash image data separately from metadata, or re-verify on metadata-only changes, so that NeoFinder edits are not flagged as corruption.

The catalog format is a closed proprietary binary (`.neofinder7`, one file per cataloged volume or folder). **No public specification or reverse-engineered parser exists** ([Backup](https://www.cdfinder.de/guide/4/4.5/neofinder_backup.html)). Data comes out as tab-delimited or indented text on any licence, or XML on the Business licence only ([Export catalogs](https://www.cdfinder.de/guide/10/export_catalogs.html)). Data can go in through documented inventory formats such as PreRoll Post CSV, LTFS XML and Hedge Canister ([Import](https://www.cdfinder.de/guide/3/3.6/import.html)). AppleScript is the only automation surface, and it is a capable one. The `catalog "<path>" with canUpdate` command re-catalogs a folder. Catalog items expose path, size, dates, **FileCheck MD5** and readable and writable XMP properties, and the `finder path` property is empty for offline items ([AppleScript dictionary](https://www.cdfinder.de/guide/9/9.1/neofinder-as-dictionary.html); [Cataloging via AppleScript](https://www.cdfinder.de/guide/9/9.5/cataloging_applescript.html)). Shared catalogs on a NAS need a Business licence and offer no locking ([Multi-user NAS setup](https://www.cdfinder.de/guide/2/2.2/neofinder_server.html)).

These facts set the integration contract. After any move, the desktop client calls `catalog … with canUpdate` on the destination folder, and on the source folder too if it survives. Users with many archive drives can import NeoFinder's text export, or walk catalogs over AppleScript, so the DAM learns what sits on unplugged drives and can match it by MD5. That calls for **computing MD5 alongside the DAM's primary hash**, purely to line up with NeoFinder's FileCheck. NeoFinder also has design lessons to offer, some by negative example. Its manual "Reconnect Catalog…" step ([Reconnect](https://www.cdfinder.de/guide/4/4.14/reconnect.html)) and Photo Mechanic Plus's split between *offline* (volume not mounted) and *missing* (path changed) ([Camera Bits](https://docs.camerabits.com/support/solutions/articles/48001162818)) both argue for identifying volumes by a stable ID, storing paths relative to that ID, and keeping previews of at least 640 px so offline assets stay browsable. Everything here runs only where macOS and the GUI app run, which means it belongs in the desktop client and could never live on the NAS.

## PhotoShelter's API works, but one upload per minute sets the pace

PhotoShelter for Photographers is a delivery and sales product with storage attached. It is not an archive tier. The plans are **Basic $10/mo (4 GB), Standard $25/mo (100 GB) and Pro $45/mo (500 GB)**, billed annually ([PhotoShelter for Photographers](https://go.photoshelter.com/photographers/)). Some third-party reviews claim unlimited storage, but both official pages say 500 GB. After cancellation, files "are eventually deleted and purged", and the trash empties every 90 days ([Support: Canceling, via search snippet](https://support.photoshelter.com/hc/en-us/articles/203373790-Downgrading-Canceling)). PhotoShelter has no official bulk export tool, which is why community migration scripts exist ([Ninkuk migration tool](https://github.com/Ninkuk/Photoshelter-Migration-Tool)). The NAS and an independent cloud copy remain the archive of record. PhotoShelter holds selects and finals.

The REST API v4 is documented, current and broad. Its OpenAPI spec was last modified in July 2026 and covers 132 paths: upload, galleries and collections, IPTC and arbitrary XMP, custom fields, rating (−1 to 5, where −1 means reject), search with `modify_start`/`modify_end`, original downloads, links, embeds and versions ([API v4 spec](https://engineering.photoshelter.com/psapi-v4-doc/photoshelter.json)). Three constraints dominate a sync design:

| Constraint | Consequence for the DAM |
|---|---|
| **"One upload per minute"** on `POST /media`, on top of a per-key rate limit (100/min in the example) | Batch several files per request with `file[]`. If each request carries one file, a 500-image gallery takes about 8.3 hours. Jobs must be resumable and run on an always-on host |
| **No checksums** in the spec; only `file_size` and `modified_at` | Keep a local hash-to-media-ID map and verify by size, or by downloading the original back |
| **No webhooks**; search capped at 10,000 results | Poll by date window to pull back client-side edits |
| Single read/write-all OAuth scope; PKCE not documented; no documented way to obtain an API key for Photographers plans | Each user requests their own key; plan for keys being Brands-only |

The `POST /media/{id}/versions` endpoint lets the DAM replace an edited export without breaking gallery membership or links. `download_image_embed=true` writes PhotoShelter-side metadata edits into downloads ([API v4 spec](https://engineering.photoshelter.com/psapi-v4-doc/photoshelter.json)). The spec contains no color-label or hierarchical-keyword field, so LrC hierarchies probably flatten to plain keywords; confirming that needs a live call. Incoming FTP, which needs a Standard or Pro plan, is a fallback that needs no API key, but it returns no media IDs ([Support: FTP Incoming, via search snippet](https://support.photoshelter.com/hc/en-us/articles/203373550-FTP-Incoming)). The competitive gap is concrete: **PhotoShelter's own Lightroom plug-in "is not compatible with Adobe Lightroom v12.4 and above"** ([Support: Lightroom Plug-in, via search snippet](https://support.photoshelter.com/hc/en-us/articles/203373590-PhotoShelter-s-Adobe-Lightroom-Plug-in)). A DAM that publishes from the NAS to PhotoShelter, and republishes when files change, would replace a broken first-party path the first user may already depend on. There is no official SDK. The community clients are tiny and mostly unlicensed, so the project will write its own connector.

## Verified movement means embedding rclone and owning the hashes

### rclone is the engine; the DAM is the ledger

Building a multi-cloud transfer engine would repeat years of rclone's work: per-backend hashing, OAuth for Drive and Dropbox, multipart uploads, character encoding. rclone's remote-control daemon (`rclone rcd`) exposes copy, sync, move and check as **async jobs with per-group stats, runtime bandwidth limits and Prometheus metrics** ([rclone rc docs](https://rclone.org/rc/)). Its safety flags map directly onto DAM policy: `--checksum`, `--immutable`, `--backup-dir`, `--max-delete`, `--track-renames`, and `--bwlimit` timetables ([rclone global flags](https://rclone.org/docs/)). Two caveats shape the integration. **rc access "is equivalent to shell access"**, so the daemon must bind to loopback with authentication. Finished jobs expire after 60 seconds by default, so the DAM must persist results in its own ledger ([rclone rc docs](https://rclone.org/rc/)). The in-process library librclone is labelled **experimental** and does not use rclone's config or logging ([librclone README](https://github.com/rclone/rclone/tree/master/librclone)), which favours running the daemon. The dedupe backup tools serve a different purpose. restic (BSD-2) and Kopia (Apache-2.0) are still pre-1.0, and their repositories cannot be browsed by photo tools ([WZ-IT comparison](https://wz-it.com/en/blog/restic-borg-kopia-backup-comparison/)), so they fit an optional versioned safety net rather than "where the asset lives". **On macOS 15.4 and later, `/usr/bin/rsync` is openrsync**, which accepts only a subset of rsync's options ([mjtsai.com](https://mjtsai.com/blog/?p=47989)). A Mac-side DAM must not depend on it.

### No single hash works everywhere, and SMB has none

| Location | Native hash | Verification route |
|---|---|---|
| NAS local disk (agent) | Any | Hash locally at full disk speed |
| **SMB share (workstation)** | **None** | Read every byte back over the LAN |
| S3 / S3-compatible | MD5 (ETag unreliable for multipart); AWS adds SHA-256, CRC64NVME and **XXHash64/3/128** checksums | Full-object checksum headers; S3 Batch "Compute checksum" verifies at rest |
| Backblaze B2 | SHA-1 (large files need the source's SHA-1) | Compute SHA-1 at ingest |
| Google Drive | MD5, SHA-1, SHA-256 | Match SHA-256 |
| Dropbox / OneDrive | Proprietary / QuickXor | rclone computes these on the fly |

Sources: [rclone overview](https://rclone.org/overview/); [AWS S3 integrity](https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity.html); [rclone B2](https://rclone.org/b2/).

The DAM should compute its own canonical hash at ingest: XXH3 or XXH64 for speed, plus SHA-256 for fixity, plus MD5 for NeoFinder FileCheck compatibility. It then verifies each copy with the strongest hash the destination offers, or falls back to a read-back. Hedge OffShoot's three modes give a ready policy ladder. *Transfer* checks size only, and Hedge warns not to use it if sources will be erased. *Source* hashes the source independently. *Source & Destination* reads back every copy, takes about twice as long, and is what ASC MHL needs ([Hedge docs](https://docs.hedge.video/offshoot/features/verification)). Hedge always records **XXH64 in big-endian form**. Tools disagree on byte order ([Pomfort KB](https://kb.pomfort.com/?p=4678)), so the DAM must state its variant when it emits manifests. Two manifest formats make every drive and bucket self-describing without the DAM. **ASC MHL** provides chain-of-custody generations and supports xxHash ([ASC MHL spec](https://cms-assets.theasc.com/ASCMHL_Specification_v1.0.pdf)). **BagIt (RFC 8493)** recommends SHA-512, requires SHA-256 support, and distinguishes "complete" bags from "valid" ones ([RFC 8493](https://www.rfc-editor.org/rfc/rfc8493.html)). A move must always be copy, then verify, then delete. Deleting a source should never be allowed after a size-only check.

### Destinations have different economics and different traps

| Destination | Price (Oct 2026) | Trap to model | Best role |
|---|---|---|---|

Sources: [Backblaze pricing](https://www.backblaze.com/cloud-storage/pricing); [Backblaze Object Lock](https://www.backblaze.com/docs/cloud-storage-object-lock); [iDrive e2](https://www.idrive.com/e2/pricing); [Wasabi FAQ](https://wasabi.com/pricing/faq); [R2 pricing](https://developers.cloudflare.com/r2/pricing/); [R2 bucket locks](https://developers.cloudflare.com/r2/buckets/bucket-locks/); [AWS Glacier](https://aws.amazon.com/s3/storage-classes/glacier/); [NASCompares C2](https://nascompares.com/2026/05/25/synologys-c2-and-license-changes-explained/). The 180-day Deep Archive minimum comes from third-party guides ([Upstash](https://upstash.com/blog/aws-s3-pricing-explained-2026)).

At these prices, a 20 TB archive costs about $139 a month on B2 and about $20 a month in Deep Archive. A sensible arrangement for a photographer is B2 or e2 with a rolling Object Lock as the restorable copy, plus optional Deep Archive for frozen years. The ledger has to record each copy's `min_retention_until` and `lock_until`, so that a "move" never triggers early-deletion fees and never fails halfway against a lock. External drives and LTO fit the same model as offline locations. Each one carries an MHL or BagIt manifest and a "last verified" date. For LTO, the DAM should export a staging set for Canister or Archiware rather than drive tape hardware itself. An LTO-9 drive costs about $5.7–8.4k ([OWC/macsales](https://eshop.macsales.com/item/OWC/TBLTMP90000H); [Newegg](https://www.newegg.com/p/35Y-00JH-00012)).

### Filenames break before bytes do

**macOS stores filenames in NFD; Linux NAS systems and Windows use NFC.** Over SMB, the mismatch produces Finder error −43 and files that look duplicated or invisible ([QNAP FAQ](https://www.qnap.com/en/how-to/faq/article/sometimes-i-get-an-error-code-43-when-attempting-to-access-files-in-a-shared-folder-while-using-finder-in-macos-via-smb-what-causes-this)). rsync's `--iconv` fix works over SSH but **not against a mounted SMB share** ([ServerFault mirror](https://kiwix.lema.org/serverfault.com_en_all_2023-11/a/427200)). rclone normalizes names when comparing, but it can skip one of a pair of names that differ only in normalization ([rclone forum](https://forum.rclone.org/t/support-for-korean-jaso-conversion/19435)). SMB, Dropbox and OneDrive are case-insensitive, while S3, B2 and Linux are case-sensitive ([rclone overview](https://rclone.org/overview/)). The DAM should key assets by content hash, store the byte-exact original name, and check for normalization and case collisions before every copy. It should flag collisions rather than silently rename anything.

## A NAS agent beats both a workstation-only DAM and a NAS-resident core

### Running a container on the photographer's NAS is not building a NAS

The distinction matters, and it should be stated plainly. A NAS product means owning hardware, an operating system, the storage stack (RAID, Btrfs or ZFS, snapshots), the SMB and NFS services, user accounts, updates, and the support burden that comes with them. Option (b) does none of this. The photographer keeps their Synology, QNAP, UGREEN, TrueNAS or Unraid box, with its firmware, shares, Hyper Backup tasks and drive pool, exactly as they are. The DAM ships an OCI image that the user adds through Container Manager, Container Station, TrueNAS Apps or Unraid Docker, the same way Immich and Jellyfin reach these users today ([Immich docs: Synology](https://docs.immich.app/install/synology/); [Jellyfin docs](https://jellyfin.org/docs/general/installation/advanced/synology)). It runs unprivileged, needs no `cap_add`, bind-mounts the photo shares, and can be removed without touching a single photo. Shipped this way, it passes UGREEN's packer rules and TrueNAS's no-host-API catalog policy by construction. It is application software that happens to run where the files are.

### The evidence favours (b) on almost every axis

| Concern | (a) Workstation-only over SMB | (b) Agent on NAS + desktop client | (c) NAS-resident core |
|---|---|---|---|
| Change detection | SMB CHANGE_NOTIFY is a hint only: it can be disabled on macOS clients ([Dell PowerScale](https://infohub.delltechnologies.com/en-au/l/powerscale-onefs-macos-client-performance-and-user-experience-optimization/smb-change-notifications-5)), and it misses changes made on the server unless Samba's kernel change notify is on, which can exhaust file descriptors ([TrueNAS forum](https://www.truenas.com/community/threads/truenas-13-and-kernel-change-notify-no.112880/)). Rescans happen over the network (an unmeasured estimate puts a 2M-file stat pass at 15–30 min on a LAN) | Local scans as source of truth; directory-level inotify within the **8192 default watch budget** ([Immich docs](https://docs.immich.app/features/libraries)); `zfs diff` as an opt-in accelerator ([OpenZFS](https://openzfs.github.io/openzfs-docs/man/master/8/zfs-diff.8.html)) | Same as (b) |
| DB-on-share risk | Safe only if the DB stays on local SSD; must refuse network paths, as SQLite advises ([sqlite.org](https://www.sqlite.org/useovernet.html)) | Agent ledger on the NAS's local volume, owned by one process; desktop cache on local SSD; never a DB across SMB | Postgres on NAS SSD; clients over HTTP |
| Cloud and NAS-to-NAS transfer | **Double hop**: NAS → laptop → internet; stops when the laptop sleeps | Direct from NAS; runs unattended | Direct from NAS |
| Verification | rclone's SMB backend has **no hashes**, so every check means reading all bytes back over the LAN ([rclone overview](https://rclone.org/overview/)) | All hashes at local disk speed; native cloud checksums | Same as (b) |
| ARM / low-RAM boxes | Works on anything, including WD My Cloud | Thin agent fits 1–2 GB ARM units (unbenchmarked) | Needs x86 and roughly 4–8 GB (Immich's floor is 6 GB); no ML on Synology without iGPU |
| Lightroom path handling | Sees the same `/Volumes/…` or `X:` paths as LrC, so it is simplest | Needs a root-mapping table (`/volume1/Photos` ↔ `/Volumes/Photos`), like Photo Mechanic's Shared Folders ([Camera Bits](https://docs.camerabits.com/en/support/solutions/articles/48001157499)) | Same mapping, plus every client OS |
| LrC SDK, `.lrcat`, NeoFinder AppleScript | Native | In the desktop client | **Still needs a desktop component** |
| PhotoShelter 1-upload/min jobs | Hours of uptime on a laptop | Background on an always-on box | Same as (b) |
| Security exposure | Minimal | Loopback/LAN API only; no internet exposure by default | A web app on the NAS; QNAP Photo Station was the DeadBolt entry point ([Malwarebytes](https://www.malwarebytes.com/blog/news/2022/09/update-now-qnap-warns-users-deadbolt-is-exploiting-photo-station-vulnerability)) |
| Multi-user, client proofing later | No | Agent can grow into (c) | Yes |

Option (a) wins on path simplicity and universality, and those strengths should be kept. It remains the mandatory fallback for WD My Cloud and for any NAS that cannot run containers, and it stays the right engine for offloads to drives plugged into the Mac. As the primary design, though, it fails the user's central requirement of *safe, verifiable* movement off the NAS. Verification costs a full read over SMB, and every upload depends on a laptop staying awake. Option (c) solves the byte problems but not the tool problems. **LrC's catalog, LrC's SDK and NeoFinder's AppleScript all exist only on the Mac**, so a NAS-resident core still needs a desktop client. On top of that it adds the heaviest hardware demands and the largest attack surface, in exchange for multi-user features a single photographer does not need yet. Option (b) puts each responsibility where the evidence says it belongs.

## Recommendation: build the ledger and bridges, embed the engines

### Architecture

The **NAS agent** is a single unprivileged multi-arch container. It holds the storage ledger: assets keyed by content hash; copies with location, relative path, status, verify method, `verified_at`, `lock_until` and `min_retention_until`; and volumes identified by stable IDs. The ledger lives in SQLite (WAL mode) or Postgres on the NAS's own volume, owned by that single process. The agent scans and hashes locally, extracts embedded JPEG previews, and runs `rclone rcd` on loopback with authentication for all NAS-originated copies. It also runs the PhotoShelter connector and the optional orchestration of native backups: TrueNAS `cloudsync.sync_onetime`, a best-effort Hyper Backup trigger, and QNAP HBS3 report-only. It computes 3-2-1 status from *verified* copies only. A Hyper Backup or HBS3 set counts as a backup but never as a browsable location.

The **desktop client**, a macOS app first because of this user, holds a rebuildable preview and search cache on local SSD and the culling and editing UI. It owns all the tool bridges: the read-only LrC catalog importer, the Lua plug-in over `LrHttp`, XMP writes with optimistic mtime checks, the NeoFinder AppleScript hooks, and a local rclone for drives attached to the Mac. **Editorial truth lives in XMP**, the format all three tools already share. **Storage truth lives in the agent's ledger.** The desktop database is a cache, so no database ever spans SMB, and the agent can later grow into a full option (c) server without a migration. For NAS boxes that cannot run containers, the desktop client runs the agent's code locally in option (a) mode, with read-back verification over SMB.

### Integration priority for this first user

| Order | Deliverable | Why first |
|---|---|---|
| 1 | Volume and root-mapping model; scan and hash on the agent; **LrC-compatible XMP read/write** (`dc:subject`, `lr:hierarchicalSubject`, `xmp:Rating` including −1, label text mapping, `mwg-rs`, embedded XMP in ARW/ORF/RW2) | It is the contract with LrC and NeoFinder at once; zero risk to their data |
| 2 | **Read-only `.lrcat` import** from a copy (flags, collections, smart-collection definitions, stacks, virtual copies) | Recovers what XMP never carries; needs only an lrcat-extractor test against the user's LrC 15 catalog |
| 3 | **Verified copy jobs**: NAS → B2/e2 with Object Lock, NAS → second NAS, Mac → external drive; MHL/BagIt manifests; copy-verify-delete moves | The core safety promise; Hedge-style verification ladder |
| 4 | **LrC plug-in**: DAM asset-ID field, "sync with DAM", relocation assist after moves, publish service | The only supported catalog write path; fixes the missing-folder problem moves create |
| 5 | **NeoFinder hooks**: re-catalog after moves; import text export or AppleScript inventory of offline drives, matched by MD5 | Keeps the user's "where is it" tool current; harvests archive-drive knowledge |
| 6 | **PhotoShelter target**: batched uploads, versions, resumable queue, poll-back of ratings and IPTC, size-based verification; FTP fallback | Replaces the plug-in that broke at LrC 12.4, but gated on the user obtaining an API key |

### Build versus embed

| Component | Decision | Note |
|---|---|---|
| Transfer engine | **Embed rclone** (`rcd` daemon) | MIT licence widely cited; not re-verified in this research |
| Hashing | Embed xxHash, SHA-256 and MD5 libraries | Declare XXH64 byte order explicitly |
| Manifests | Build BagIt writer; embed or port ASC MHL | Reference implementation `ascmhl` is Python ([ascmhl docs](https://ascmhl.readthedocs.io/en/latest/README.html)) |
| LrC catalog reader | Embed lrcat-extractor (MPL-2.0) or a thin SQL layer | Verify LrC 12–15 coverage first |
| XMP read/write | Embed ExifTool or Exiv2 | Licences unverified; Exiv2 is believed to be GPL, so audit before choosing the project licence |
| Storage ledger, verification policy, 3-2-1 engine | **Build** | The DAM's differentiator |
| LrC Lua plug-in | **Build** | Use lrc-immich-plugin as a pattern reference |
| NeoFinder bridge | **Build** (thin AppleScript) | Never parse `.neofinder7` |
| PhotoShelter connector | **Build** | No official SDK; community clients mostly unlicensed |
| Versioned dedupe backup | Optional embed of restic or Kopia | Safety net, not an asset location |
| NAS-native backup, LTO | **Orchestrate / export only** | TrueNAS API; Hyper Backup undocumented; LTO via Canister/P5 staging |

Several questions remain open and should be resolved early. Does lrcat-extractor read LrC 15 catalogs? Can the LrC SDK relocate folders? How does a Photographers-plan user get a PhotoShelter API key, and does "one upload per minute" count requests or files? Which brand and model of NAS does the first user own? That last answer decides whether their box can host more than a thin agent, and whether any of its specs fall in a † cell above.

## Conclusion

The question "should the DAM run on the NAS?" turns out to be two questions, and they have opposite answers. Everything that touches the photographer's *tools* must run on the workstation, because Adobe, NeoFinder's developer and the SQLite authors have each put their critical surfaces there: a catalog that cannot live on a network volume, an SDK that runs inside the desktop app, and automation that exists only as macOS AppleScript. Everything that touches the photographer's *bytes* should run on the NAS, because SMB offers no hashes, no reliable change events and no way around the double hop. Treating the agent as a ledger of facts about bytes, rather than as a NAS-hosted app, keeps the project out of the NAS business while giving it the one capability that photographers' existing tools lack: provable answers to "how many verified copies of this shoot exist, where are they, and when were they last checked?"

The integrations look less like adapters for three products and more like one contract (XMP plus content hashes) with three thin bridges. Each bridge also has an opening. PhotoShelter's own Lightroom plug-in is officially incompatible with current LrC. NeoFinder writes into raw files that other tools assume are untouched. LrC's UNC-path bug was still being reported in 2025, six years after it first appeared. The DAM's value for this first user lies less in replacing any of these tools than in tracking what passes between them.
